## 1. Описание проекта

### 1.1. Назначение
Веб-приложение с интеллектуальным ассистентом, который консультирует граждан по вопросам защиты прав потребителей на основе нормативных документов РФ и формирует черновики претензий. Ответы строятся по технологии RAG: языковая модель отвечает только на основе найденных фрагментов документов и указывает источники.

### 1.2. Границы MVP
**Входит:** чат-консультация с контекстом диалога, источники со сносками, корректный отказ, черновик претензии (текст с кнопкой «Копировать»), оценка ответов, загрузка базы знаний скриптом.
**Следующая итерация:** авторизация и история диалогов, веб-интерфейс администратора для документов, карточки типовых ситуаций.
**По возможности (Nice to have):** скачивание претензии в .docx (US-10), статистика качества (US-11).
**Не входит:** голосовой ввод, оплата, другие отрасли права, мобильное приложение.

### 1.3. Стек
| Слой | Технологии |
|---|---|
| Frontend | React 18, TypeScript (strict), Vite, Tailwind CSS, React Router, TanStack Query |
| Backend | Python 3.11, FastAPI, Pydantic v2, SQLAlchemy 2 (async) |
| БД | PostgreSQL 16 + pgvector (Supabase) |
| Авторизация | Supabase Auth (OAuth: Яндекс ID, Google) |
| RAG | BGE-M3 через Ollama (эмбеддинги, 1024), гибридный поиск (вектор + полнотекстовый `russian`), реранкер bge-reranker-v2-m3 в процессе backend |
| LLM | Ollama, открытая модель 7–8B (Qwen); резерв — OpenRouter через общий интерфейс `LLMClient` (только для чата, не для претензий) |
| Генерация .docx | python-docx |
| Инфраструктура | Docker, docker-compose, GitHub Actions |

### 1.4. Архитектура
```
Браузер (React SPA)
   │  REST JSON + SSE (стриминг ответа)
   ▼
FastAPI ── api/ → services/ → repositories/ ──► PostgreSQL + pgvector
   │              │
   │              ├─ rag/  (нарезка, эмбеддинги, поиск, реранкер bge-reranker-v2-m3, сборка промпта)
   │              └─ llm/  (LLMClient: OllamaClient | OpenRouterClient)
   ▼
Ollama: языковая модель Qwen 7–8B + модель эмбеддингов bge-m3
```

### 1.5. База знаний (исходные документы)
1. Закон РФ от 07.02.1992 № 2300-1 «О защите прав потребителей».
2. Правила продажи товаров по договору розничной купли-продажи (Постановление Правительства РФ № 2463 от 31.12.2020), включая перечень непродовольственных товаров надлежащего качества, не подлежащих обмену.
3. Перечень технически сложных товаров (Постановление Правительства РФ № 924 от 10.11.2011).
4. Постановление Пленума Верховного Суда РФ от 28.06.2012 № 17.

Для каждого документа хранится дата редакции; в интерфейсе показывается дата актуальности базы — максимальная дата редакции среди активных документов (`GET /api/kb/info`).

**Источник и нарезка.** Тексты берутся из открытых источников (pravo.gov.ru, КонсультантПлюс) и хранятся в репозитории в `data/` в формате .txt с датой редакции. Служебные пометки справочных систем («в ред.», «см. текст в предыдущей редакции») удаляются. Правила нарезки:
- закон — по статьям; статья длиннее 1500 символов делится по пунктам, номер статьи сохраняется в каждой части (реализовано в `backend/app/rag/chunking.py`);
- Постановление Пленума — по пунктам;
- перечни и Правила продажи — по пунктам и разделам.

Поле `chunks.article` хранит номер структурной единицы (статьи или пункта).

### 1.6. Эталонный стенд и план работ
Требования к скорости (раздел 4) проверяются бенчмарком на эталонном стенде — машине разработчика: NVIDIA RTX 3070 Ti (8 ГБ VRAM), 64 ГБ ОЗУ. Бюджет видеопамяти: Qwen 7–8B в квантовании Q4 (около 5 ГБ), bge-m3 (около 1,2 ГБ), реранкер (около 1 ГБ; при нехватке VRAM запускается на CPU). На других машинах тайминги служат ориентиром.

## 3. Функциональные требования

### F1. Чат-консультация (US-01, US-02)

**Описание.** Пользователь отправляет вопрос; система находит релевантные фрагменты, формирует ответ языковой моделью и возвращает его потоково вместе с источниками.

**Алгоритм обработки вопроса:**
1. Валидация: 10–2000 символов после `strip()`; проверка, что `conversation_id` принадлежит текущему клиенту (`client_id` гостя или `user_id`), иначе 404.
2. Анализ вопроса одним вызовом LLM с учётом истории диалога → JSON `{ "on_topic": bool, "search_query": "string" }`. История нужна, чтобы короткие уточнения («А если откажут?») не получали ложный отказ; объединение классификации и переформулировки экономит один вызов модели. Если `on_topic = false` — отказ типа `off_topic` (см. F3).
3. Гибридный поиск по `search_query`: топ-20 по вектору + топ-20 полнотекстово → объединение (RRF) → реранкер → топ-5.
4. Score реранкера приводится к диапазону 0..1 (sigmoid). Если максимальный score < `RELEVANCE_THRESHOLD` (по умолчанию 0.3, из env; калибруется на контрольном наборе) — отказ типа `no_context` (см. F3).
5. Сборка промпта: системная инструкция + фрагменты с номерами [1]…[5] + история + вопрос. Фрагменты и вопрос пользователя отделяются явными маркерами (защита от инструкций внутри вопроса). Инструкция требует отвечать только по фрагментам, ставить сноски [n], пояснять юридические термины простыми словами и заканчивать блоком «Что делать дальше».
6. Контекст модели: `num_ctx = 8192` токенов. Бюджет: системная инструкция ≤ 500, фрагменты ≤ 3000, история ≤ 2000, вопрос ≤ 1000, остальное — ответ. История — последние 10 сообщений (реплик пользователя и ассистента); если они не влезают в бюджет, отбрасываются самые старые. Ollama при переполнении молча обрезает начало промпта вместе с системной инструкцией, поэтому бюджет проверяется до вызова модели.
7. Потоковая генерация ответа (SSE). Если клиент закрыл соединение, генерация отменяется, а ответ сохраняется со статусом `interrupted`.
8. Постобработка: из ответа извлекаются использованные сноски; источники, на которые нет ссылок, не показываются; сноски на несуществующие номера удаляются из сохраняемого текста. Клиент делает сноски кликабельными только после события `sources` и не отображает сноски без пары.
9. Сохранение сообщения пользователя, ответа (со статусом) и связей с фрагментами в БД.

Ошибки до начала потока (валидация, лимит запросов, чужой диалог) возвращаются HTTP-кодом и JSON из п. 5.1, после начала потока — событием `error`.

**API:**
- `POST /api/chat/ask` → `text/event-stream`
  - запрос: `{ "conversation_id": "uuid | null", "question": "string", "retry_message_id": "uuid | null" }`; `retry_message_id` передаётся кнопкой «Сгенерировать заново»: вопрос не дублируется, прерванный ответ заменяется новым
  - события: `meta { conversation_id, message_id }`, `token { text }`, `sources { items: Source[] }`, `refusal { type, message }`, `done {}`, `error { code, message }`
  - `Source = { "n": 1, "document_title": "...", "article": "18", "article_title": "...", "excerpt": "...", "chunk_id": "uuid" }`
- `POST /api/conversations` → `{ "id": "uuid" }` — новая консультация.
- `GET /api/kb/info` → `{ "edition_date": "YYYY-MM-DD", "documents": [{ "title": "...", "edition_date": "..." }] }` — дата актуальности базы для шапки.
- `GET /api/health` → `{ "status": "ok" }` — проверка для docker и CI.

**Frontend:** поле ввода со счётчиком символов; индикатор «Ищу в законе…» до первого токена; кнопка «Новая консультация»; автопрокрутка к новому сообщению. Поток читается через `fetch` + `ReadableStream`: нативный `EventSource` не поддерживает POST. Сервер отдаёт заголовок `X-Accel-Buffering: no`, чтобы прокси не буферизовал поток. В MVP гостевой диалог после перезагрузки страницы не восстанавливается.

### F2. Источники (US-03)

**Описание.** Отображение статей, на которые опирается ответ.

- Сноски [n] в тексте ответа — кликабельные.
- Десктоп (≥ 768px): правая панель «Источники» (40% ширины) с карточками: документ, «Статья N. Название», цитата (до 600 символов) с подсветкой; клик по сноске прокручивает к карточке и подсвечивает её на 2 с.
- Мобильный (< 768px): кнопка «Источники (N)» открывает bottom sheet.
- `GET /api/chunks/{chunk_id}` → полный текст фрагмента для «Открыть полный текст».

### F3. Корректный отказ (US-04)

| Тип | Условие | Сообщение пользователю |
|---|---|---|
| `off_topic` | классификатор: вопрос не по теме | «Этот вопрос не относится к защите прав потребителей. Рекомендуем обратиться к юристу.» |
| `no_context` | нет фрагментов выше порога | «В моей базе нет точного ответа на этот вопрос. Попробуйте переформулировать или обратитесь в Роспотребнадзор» + ссылка |

- При отказе LLM не генерирует ответ по существу, источники не показываются.
- Отказ сохраняется в БД с типом (нужно для статистики F7 и метрики «корректный отказ» в магистерской).
- Дисклеймер «Справочная информация, не замена консультации юриста» постоянно виден в шапке.

### F4. Черновик претензии (US-05, US-10)

**Форма** (единый список полей, US-05 ссылается на него): ФИО (обяз.), адрес или e-mail для ответа (обяз.), продавец — название и адрес (обяз.), товар/услуга (обяз.), дата покупки (обяз., не в будущем), суть проблемы (обяз., 20–2000 символов), требование (обяз.: замена / ремонт / возврат денег / уменьшение цены / иное + текст). «Суть проблемы» предзаполняется текстом первого вопроса пользователя в диалоге, без вызова LLM.

**API:**
- `POST /api/claims/draft` — запрос: данные формы + `conversation_id` (опц.); ответ: `{ "text": "...", "sources": Source[] }`. Лимит — 10 претензий в час на клиента.
- `POST /api/claims/docx` (US-10, Nice to have) — запрос: `{ "text": "..." }`; ответ: файл `application/vnd.openxmlformats-officedocument.wordprocessingml.document`, заголовок `Content-Disposition: attachment; filename="pretenziya_<YYYY-MM-DD>.docx"`, в конце документа — поля для подписи и даты.

**Правила генерации:** поиск статей выполняется по сути проблемы и требованию. Шапка (ФИО, адрес, продавец), требование и срок ответа подставляются backend по шаблону для типа требования: 7 дней — замена (ст. 21), 10 дней — возврат денег и уменьшение цены (ст. 22), не более 45 дней — ремонт (ст. 20). LLM пишет только описание ситуации и правовое обоснование со ссылками. Персональные данные в LLM не передаются, в БД и логи не пишутся. Резервная облачная модель для претензий не используется.

### F5. Оценка ответов (US-06)

- `POST /api/messages/{message_id}/feedback` — `{ "rating": "up" | "down", "comment": "string | null" }`.
- Одна оценка на сообщение от одного клиента (гость — по `client_id` из localStorage, пользователь — по `user_id`); повторная оценка обновляет запись (upsert).
- Комментарий до 500 символов.

### F6. Авторизация и история (US-08) — Should have

- Вход через Supabase Auth (Яндекс ID, Google); backend проверяет JWT Supabase. Яндекс ID нет среди встроенных провайдеров Supabase — нужна отдельная OIDC-интеграция; если на неё не хватит времени, первая версия F6 работает только с Google.
- `GET /api/conversations` — список своих диалогов `{ id, title, updated_at }`, сортировка по `updated_at` (новые сверху), пагинация по 20; `title` — первые 60 символов первого вопроса.
- `GET /api/conversations/{id}` — сообщения с источниками.
- `DELETE /api/conversations/{id}` — удаление своего диалога.
- Гостевые диалоги в истории не отображаются; хранятся 30 дней, затем удаляются. Перед удалением обезличенные данные об отказах (тип отказа, дата, длина вопроса) остаются в таблице `refusal_events` — они нужны для статистики и метрики «корректный отказ».

### F7. Администрирование базы знаний (US-09, US-11) — Should / Nice

- MVP: CLI `python -m app.rag.indexer --file <path> --key <document_key> --title <...> --edition-date <YYYY-MM-DD>`.
- Документ определяется стабильным ключом `key` (например, `zozpp`), а не названием. Новая редакция с тем же `key` переводит старую в статус `archived` и исключает её из поиска — одинаково для CLI и веб-интерфейса.
- Веб-интерфейс `/admin`:
  - `POST /api/admin/documents` (multipart: файл .txt/.pdf/.docx ≤ 10 МБ, key, title, edition_date) → индексация в фоне;
  - `GET /api/admin/documents` — список со статусами `indexing | ready | failed | archived` и текстом ошибки для `failed`;
  - `POST /api/admin/documents/{id}/reindex` — повторная индексация (кнопка «Повторить индексацию»);
  - `GET /api/admin/stats?from=&to=` — доля оценок «up», число отказов по типам, топ-20 вопросов с отказом (дословные вопросы, без кластеризации по темам).
- Разбор загружаемых PDF и DOCX ограничен по размеру (10 МБ) и времени (60 с на файл).

### F8. Типовые ситуации (US-07) — Should have, следующая итерация

- На стартовом экране 6 карточек («Сломался товар», «Хочу вернуть товар», «Навязали услугу» и др.) с иконками, шрифт от 17px.
- Список карточек статический во frontend; нажатие подставляет начало вопроса в поле ввода и ставит курсор в конец. Backend не нужен.

### Модель данных

| Таблица | Поля |
|---|---|
| `profiles` | `id` (= auth.users.id), `role` (`user`/`admin`), `created_at` |
| `conversations` | `id`, `user_id` (nullable), `client_id`, `title`, `created_at`, `updated_at` |
| `messages` | `id`, `conversation_id`, `role` (`user`/`assistant`), `content`, `status` (`complete`/`interrupted`/`error`), `refusal_type` (nullable), `latency_ms`, `model_name`, `created_at` |
| `message_sources` | `message_id`, `chunk_id`, `n`, `score` |
| `documents` | `id`, `key`, `title`, `edition_date`, `status`, `error_message` (nullable), `source_file`, `chunks_count`, `created_at`, `updated_at` |
| `chunks` | `id`, `document_id`, `article`, `article_title`, `part`, `content`, `embedding vector(1024)`, `tsv tsvector` |
| `feedback` | `id`, `message_id`, `user_id` (nullable), `client_id`, `rating`, `comment`, `created_at`; уникальность: (`message_id`, `user_id`) для пользователей и (`message_id`, `client_id`) для гостей — частичные индексы |
| `refusal_events` | `id`, `refusal_type`, `question_length`, `created_at` — обезличенная статистика отказов |

Индексы: HNSW по `chunks.embedding` (cosine), GIN по `chunks.tsv`.
Доступ к данным: основная защита — проверка владельца в backend (фильтр по `user_id`/`client_id` в `repositories/`), потому что backend подключается к БД сервисной ролью и обходит RLS. RLS — вторая линия защиты при прямом доступе через Supabase: `conversations`, `messages`, `message_sources`, `feedback` — пользователь видит только свои строки; `documents`, `chunks` — запись только `admin`.

## 4. Нефункциональные требования

### Общие
- **Адаптивность:** корректное отображение от 360px до 1920px; mobile-first.
- **Доступность:** базовый шрифт 17px, контраст не ниже WCAG 2.1 AA, все интерактивные элементы доступны с клавиатуры, у иконок есть `aria-label`.
- **Безопасность:** секреты только в env; CORS — только домен фронтенда; параметризованные SQL-запросы; заголовки безопасности (CSP, X-Content-Type-Options); лимиты запросов считаются по паре IP + `client_id` (счётчики в памяти процесса, один экземпляр backend); вопрос пользователя отделяется от инструкций в промпте маркерами, есть негативные тесты на попытки переопределить инструкции.
- **Приватность:** текст вопросов и данные претензий не пишутся в логи; данные претензий не передаются в LLM и не сохраняются. Вопросы хранятся в `messages` и при локальной модели не покидают сервер. Место хостинга БД (Supabase Cloud или self-hosted) и требования 152-ФЗ — открытый вопрос (раздел 7).
- **Совместимость:** последние 2 версии Chrome, Firefox, Safari, Яндекс Браузера.
- **Тестирование:** покрытие модулей `rag/` и `services/` тестами ≥ 70%. В CI реальные модели не запускаются: используются `FakeLLMClient`, заранее сохранённые эмбеддинги и контейнер PostgreSQL + pgvector.

### По функциям
| Функция | Требования |
|---|---|
| F1 Чат | на эталонном стенде (п. 1.6): время до первого токена ≤ 5 с (p95), полный ответ ≤ 25 с; общий бюджет на запрос 60 с; ограничение 20 вопросов в час на гостя и 60 на пользователя; ответ на русском языке; до 10 сообщений истории в контексте |

## 5. Обработка ошибок

### 5.1. Формат ошибки API
```json
{ "error": { "code": "VALIDATION_ERROR", "message": "Текст для пользователя на русском", "details": {} } }
```
В SSE-потоке — событие `error` с тем же объектом.

### 5.2. Таблица сценариев

| # | Ситуация | HTTP / код | Поведение системы | UX-решение |
|---|---|---|---|---|
| 1 | Пустой вопрос | — (клиент) | запрос не отправляется | кнопка «Отправить» неактивна |
| 2 | Вопрос > 2000 символов | 422 `VALIDATION_ERROR` | отклонение до поиска | красный счётчик, подсказка «Сократите описание до 2000 символов» |
| 3 | Ошибки в форме претензии | 422 `VALIDATION_ERROR` + `details` по полям | отклонение | подсветка полей, сообщение под каждым полем, фокус на первое ошибочное |
| 4 | Вопрос не по теме | 200, событие `refusal: off_topic` | LLM не отвечает по существу | серая плашка с рекомендацией обратиться к юристу |
| 5 | Нет релевантных фрагментов | 200, событие `refusal: no_context` | LLM не вызывается для ответа | плашка «В базе нет точного ответа» + ссылка на Роспотребнадзор + кнопка «Переформулировать» |
| 6 | Пустая история диалогов | 200, пустой список | — | иллюстрация и текст «Здесь появятся ваши консультации» + кнопка «Задать вопрос» |
| 7 | Нет данных статистики | 200, пустые ряды | — | «Нет данных за выбранный период» вместо графиков |
| 8 | Нет сети у клиента | — (клиент) | запрос не уходит | баннер «Нет подключения к интернету», введённый текст сохраняется, кнопка «Повторить» |
| 9 | LLM недоступна / таймаут | до начала потока — 503 `LLM_UNAVAILABLE` / 504 `LLM_TIMEOUT`; после — событие `error` с тем же кодом | 1 автоматический повтор и переключение на резервный `LLMClient` — только до первого токена и в пределах общего бюджета 60 с | «Ассистент временно недоступен, попробуйте через минуту», вопрос остаётся в поле ввода |
| 10 | Обрыв SSE посреди ответа | событие `error` или закрытие потока | ответ сохраняется со статусом `interrupted`, генерация на сервере отменяется | показать полученный текст с пометкой «Ответ прерван» и кнопкой «Сгенерировать заново» (повторный запрос с `retry_message_id`) |
| 11 | Внутренняя ошибка сервера | 500 `INTERNAL_ERROR` | логирование с `request_id` | «Что-то пошло не так. Код ошибки: {request_id}» + «Повторить» |
| 12 | Превышен лимит запросов | 429 `RATE_LIMITED` + `Retry-After` | запрос отклонён | «Вы задали много вопросов подряд. Попробуйте через N мин.» |
| 13 | Не авторизован (история) | 401 `UNAUTHORIZED` | — | экран «Войдите, чтобы сохранять консультации» с кнопками входа |
| 14 | Истёк токен | 401 `TOKEN_EXPIRED` | клиент пробует обновить токен через Supabase, при неудаче — выход | «Сессия истекла, войдите снова», текущий ввод не теряется |
| 15 | Нет прав (админка) | 403 `FORBIDDEN` | — | страница «Недостаточно прав» + ссылка на главную |
| 16 | Чужой или несуществующий диалог | 404 `NOT_FOUND` | данные не раскрываются | «Консультация не найдена» + ссылка «Мои консультации» |
| 17 | Неподдерживаемый файл / > 10 МБ | 415 / 413 | файл отклонён | проверка на клиенте до отправки, сообщение с допустимыми форматами и размером |
| 18 | Ошибка индексации документа | статус `failed` | старая редакция остаётся активной | красный статус «Ошибка» и текст причины, кнопка «Повторить индексацию» |
| 19 | Ошибка генерации .docx | 500 `DOCX_ERROR` | — | «Не удалось создать файл, скопируйте текст»; «Копировать» доступна |
| 20 | Не сохранилась оценка | 5xx | — | toast «Не удалось сохранить оценку», чат работает дальше |
| 21 | Вопрос короче 10 символов | 422 `VALIDATION_ERROR` (если клиентская проверка обойдена) | отклонение до поиска | кнопка «Отправить» неактивна, подсказка «Опишите ситуацию подробнее — хотя бы 10 символов» |

### 5.3. Логирование
- Формат JSON: `timestamp`, `level`, `request_id`, `endpoint`, `status`, `latency_ms`, `model_name`, `question_length`, `refusal_type`.
- Запрещено логировать текст вопросов, ответов и данные претензий.
- Ошибки уровня `error` содержат стектрейс и `request_id`, который показывается пользователю.
