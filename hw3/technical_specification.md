Версия 1.0 · Документ подготовлен для работы с AI-агентом (Claude Code) вместе с файлом правил `CLAUDE.md` из ДЗ 2.

Связанные документы: `project_description.md`, `user_stories.md`, `ui_concepts/ui_description.md`.

## 1. Описание проекта

### 1.1. Назначение
Веб-приложение с интеллектуальным ассистентом, который консультирует граждан по вопросам защиты прав потребителей на основе нормативных документов РФ и формирует черновики претензий. Ответы строятся по технологии RAG: языковая модель отвечает только на основе найденных фрагментов документов и указывает источники.

### 1.2. Границы MVP
**Входит:** чат-консультация с контекстом диалога, источники со сносками, корректный отказ, черновик претензии, оценка ответов, загрузка базы знаний скриптом.
**Следующая итерация:** авторизация и история диалогов, веб-интерфейс администратора для документов, карточки типовых ситуаций.
**Не входит:** голосовой ввод, оплата, другие отрасли права, мобильное приложение.

### 1.3. Стек
| Слой | Технологии |
|---|---|
| Frontend | React 18, TypeScript (strict), Vite, Tailwind CSS, React Router, TanStack Query |
| Backend | Python 3.11, FastAPI, Pydantic v2, SQLAlchemy 2 (async) |
| БД | PostgreSQL 16 + pgvector (Supabase) |
| Авторизация | Supabase Auth (OAuth: Яндекс ID, Google) |
| RAG | BGE-M3 (эмбеддинги, 1024), гибридный поиск (вектор + полнотекстовый `russian`), реранкер bge-reranker |
| LLM | Ollama, открытая модель 7–8B (Qwen); резерв — OpenRouter / YandexGPT через общий интерфейс `LLMClient` |
| Генерация .docx | python-docx |
| Инфраструктура | Docker, docker-compose, GitHub Actions |

### 1.4. Архитектура
```
Браузер (React SPA)
   │  REST JSON + SSE (стриминг ответа)
   ▼
FastAPI ── api/ → services/ → repositories/ ──► PostgreSQL + pgvector
   │              │
   │              ├─ rag/  (нарезка, эмбеддинги, поиск, реранкинг, сборка промпта)
   │              └─ llm/  (LLMClient: OllamaClient | OpenRouterClient)
   ▼
Ollama (локальная модель)
```

### 1.5. База знаний (исходные документы)
1. Закон РФ от 07.02.1992 № 2300-1 «О защите прав потребителей».
2. Правила продажи товаров по договору розничной купли-продажи (Постановление Правительства РФ № 2463 от 31.12.2020), включая перечень непродовольственных товаров надлежащего качества, не подлежащих обмену.
3. Перечень технически сложных товаров (Постановление Правительства РФ № 924 от 10.11.2011).
4. Постановление Пленума Верховного Суда РФ от 28.06.2012 № 17.

Для каждого документа хранится дата редакции; в интерфейсе показывается дата актуальности базы.

## 3. Функциональные требования

### F1. Чат-консультация (US-01, US-02)

**Описание.** Пользователь отправляет вопрос; система находит релевантные фрагменты, формирует ответ языковой моделью и возвращает его потоково вместе с источниками.

**Алгоритм обработки вопроса:**
1. Валидация: 10–2000 символов после `strip()`.
2. Классификация темы: запрос к LLM «относится ли вопрос к защите прав потребителей» → `on_topic: bool`. Если `false` — отказ типа `off_topic` (см. F3).
3. Переформулировка вопроса с учётом последних 10 сообщений диалога в самостоятельный поисковый запрос.
4. Гибридный поиск: топ-20 по вектору + топ-20 полнотекстово → объединение (RRF) → реранкер → топ-5.
5. Если максимальный score реранкера < `RELEVANCE_THRESHOLD` (по умолчанию 0.3, из env) — отказ типа `no_context` (см. F3).
6. Сборка промпта: системная инструкция + фрагменты с номерами [1]…[5] + история + вопрос. Инструкция требует отвечать только по фрагментам, ставить сноски [n], заканчивать блоком «Что делать дальше».
7. Потоковая генерация ответа (SSE).
8. Постобработка: из ответа извлекаются использованные сноски; источники, на которые нет ссылок, не показываются; сноски на несуществующие номера удаляются.
9. Сохранение сообщения пользователя, ответа и связей с фрагментами в БД.

**API:**
- `POST /api/chat/ask` → `text/event-stream`
  - запрос: `{ "conversation_id": "uuid | null", "question": "string" }`
  - события: `meta { conversation_id, message_id }`, `token { text }`, `sources { items: Source[] }`, `refusal { type, message }`, `done {}`, `error { code, message }`
  - `Source = { "n": 1, "document_title": "...", "article": "18", "article_title": "...", "excerpt": "...", "chunk_id": "uuid" }`
- `POST /api/conversations` → `{ "id": "uuid" }` — новая консультация.

**Frontend:** поле ввода со счётчиком символов; индикатор «Ищу в законе…» до первого токена; кнопка «Новая консультация»; автопрокрутка к новому сообщению.

### F2. Источники (US-03)

**Описание.** Отображение статей, на которые опирается ответ.

- Сноски [n] в тексте ответа — кликабельные.
- Десктоп (≥ 768px): правая панель «Источники» (40% ширины) с карточками: документ, «Статья N. Название», цитата (до 600 символов) с подсветкой; клик по сноске прокручивает к карточке и подсвечивает её на 2 с.
- Мобильный (< 768px): кнопка «Источники (N)» открывает bottom sheet.
- `GET /api/chunks/{chunk_id}` → полный текст фрагмента для «Открыть полный текст».

### F3. Корректный отказ (US-04)

| Тип | Условие | Сообщение пользователю |
|---|---|---|
| `off_topic` | классификатор: вопрос не по теме | «Этот вопрос не относится к защите прав потребителей. Рекомендуем обратиться к юристу.» |
| `no_context` | нет фрагментов выше порога | «В моей базе нет точного ответа на этот вопрос. Попробуйте переформулировать или обратитесь в Роспотребнадзор» + ссылка |

- При отказе LLM не генерирует ответ по существу, источники не показываются.
- Отказ сохраняется в БД с типом (нужно для статистики F7 и метрики «корректный отказ» в магистерской).
- Дисклеймер «Справочная информация, не замена консультации юриста» постоянно виден в шапке.

### F4. Черновик претензии (US-05, US-10)

**Форма:** ФИО (обяз.), адрес или e-mail для ответа (обяз.), продавец — название и адрес (обяз.), товар/услуга (обяз.), дата покупки (обяз., не в будущем), суть проблемы (обяз., 20–2000 символов, предзаполняется кратким пересказом диалога), требование (обяз.: замена / ремонт / возврат денег / уменьшение цены / иное + текст).

**API:**
- `POST /api/claims/draft` — запрос: данные формы + `conversation_id` (опц.); ответ: `{ "text": "...", "sources": Source[] }`.
- `POST /api/claims/docx` — запрос: `{ "text": "..." }`; ответ: файл `application/vnd.openxmlformats-officedocument.wordprocessingml.document`.

**Правила генерации:** поиск статей выполняется по сути проблемы и требованию; LLM заполняет структуру «шапка → описание → правовое обоснование со ссылками → требование и срок → дата, подпись»; персональные данные передаются только в LLM-запрос и в ответ, в БД и логи не пишутся.

### F5. Оценка ответов (US-06)

- `POST /api/messages/{message_id}/feedback` — `{ "rating": "up" | "down", "comment": "string | null" }`.
- Одна оценка на сообщение от одного клиента (гость — по `client_id` из localStorage, пользователь — по `user_id`); повторная оценка обновляет запись (upsert).
- Комментарий до 500 символов.

### F6. Авторизация и история (US-08) — Should have

- Вход через Supabase Auth (Яндекс ID, Google); backend проверяет JWT Supabase.
- `GET /api/conversations` — список своих диалогов `{ id, title, updated_at }`, пагинация по 20.
- `GET /api/conversations/{id}` — сообщения с источниками.
- `DELETE /api/conversations/{id}` — удаление своего диалога.
- Гостевые диалоги в истории не отображаются; хранятся 30 дней для статистики, затем удаляются.

### F7. Администрирование базы знаний (US-09, US-11) — Should / Nice

- MVP: CLI `python -m app.rag.indexer --file <path> --title <...> --edition-date <YYYY-MM-DD>`.
- Веб-интерфейс `/admin`:
  - `POST /api/admin/documents` (multipart: файл .txt/.pdf/.docx ≤ 10 МБ, title, edition_date) → индексация в фоне;
  - `GET /api/admin/documents` — список со статусами `indexing | ready | failed | archived`;
  - при загрузке новой редакции документа с тем же `title` старая получает статус `archived` и исключается из поиска;
  - `GET /api/admin/stats?from=&to=` — доля оценок «up», число отказов по типам, топ-20 вопросов с отказом.

### Модель данных

| Таблица | Поля |
|---|---|
| `profiles` | `id` (= auth.users.id), `role` (`user`/`admin`), `created_at` |
| `conversations` | `id`, `user_id` (nullable), `client_id`, `title`, `created_at`, `updated_at` |
| `messages` | `id`, `conversation_id`, `role` (`user`/`assistant`), `content`, `refusal_type` (nullable), `latency_ms`, `model_name`, `created_at` |
| `message_sources` | `message_id`, `chunk_id`, `n`, `score` |
| `documents` | `id`, `title`, `edition_date`, `status`, `chunks_count`, `created_at` |
| `chunks` | `id`, `document_id`, `article`, `article_title`, `part`, `content`, `embedding vector(1024)`, `tsv tsvector` |
| `feedback` | `id`, `message_id`, `user_id` (nullable), `client_id`, `rating`, `comment`, `created_at`; unique (`message_id`, `client_id`) |

Индексы: HNSW по `chunks.embedding` (cosine), GIN по `chunks.tsv`.
RLS: `conversations`, `messages` — пользователь видит только свои строки; `documents`, `chunks` — запись только `admin`.

## 4. Нефункциональные требования

### Общие
- **Адаптивность:** корректное отображение от 360px до 1920px; mobile-first.
- **Доступность:** базовый шрифт 17px, контраст не ниже WCAG 2.1 AA, все интерактивные элементы доступны с клавиатуры, у иконок есть `aria-label`.
- **Безопасность:** секреты только в env; CORS — только домен фронтенда; параметризованные SQL-запросы; заголовки безопасности (CSP, X-Content-Type-Options).
- **Приватность:** текст вопросов и данные претензий не пишутся в логи; при локальной модели данные не покидают сервер.
- **Совместимость:** последние 2 версии Chrome, Firefox, Safari, Яндекс Браузера.
- **Тестирование:** покрытие модулей `rag/` и `services/` тестами ≥ 70%.

### По функциям
| Функция | Требования |
|---|---|
| F1 Чат | время до первого токена ≤ 5 с (p95, локальная модель на GPU); полный ответ ≤ 25 с; таймаут генерации 60 с; ограничение 20 вопросов в час на гостя и 60 на пользователя; ответ на русском языке; до 10 сообщений истории в контексте |
| F2 Источники | открытие панели/шторки ≤ 200 мс; каждая показанная сноска соответствует реальному фрагменту (0 «висячих» ссылок) |
| F3 Отказ | решение об отказе ≤ 3 с; порог релевантности настраивается через env без перезапуска сборки |
| F4 Претензия | генерация ≤ 30 с; .docx ≤ 3 с; персональные данные не сохраняются (проверяется тестом репозитория) |
| F5 Оценка | сохранение ≤ 500 мс; сбой сохранения не блокирует чат |
| F6 История | загрузка списка ≤ 1 с; доступ к чужим данным невозможен (RLS + проверка на backend) |
| F7 Админка | индексация документа 100 страниц ≤ 5 мин; загрузка файла ≤ 10 МБ; доступ только роли `admin` |

## 5. Обработка ошибок

### 5.1. Формат ошибки API
```json
{ "error": { "code": "VALIDATION_ERROR", "message": "Текст для пользователя на русском", "details": {} } }
```
В SSE-потоке — событие `error` с тем же объектом.

### 5.2. Таблица сценариев

| # | Ситуация | HTTP / код | Поведение системы | UX-решение |
|---|---|---|---|---|
| 1 | Пустой вопрос | — (клиент) | запрос не отправляется | кнопка «Отправить» неактивна |
| 2 | Вопрос > 2000 символов | 422 `VALIDATION_ERROR` | отклонение до поиска | красный счётчик, подсказка «Сократите описание до 2000 символов» |
| 3 | Ошибки в форме претензии | 422 `VALIDATION_ERROR` + `details` по полям | отклонение | подсветка полей, сообщение под каждым полем, фокус на первое ошибочное |
| 4 | Вопрос не по теме | 200, событие `refusal: off_topic` | LLM не отвечает по существу | серая плашка с рекомендацией обратиться к юристу |
| 5 | Нет релевантных фрагментов | 200, событие `refusal: no_context` | LLM не вызывается для ответа | плашка «В базе нет точного ответа» + ссылка на Роспотребнадзор + кнопка «Переформулировать» |
| 6 | Пустая история диалогов | 200, пустой список | — | иллюстрация и текст «Здесь появятся ваши консультации» + кнопка «Задать вопрос» |
| 7 | Нет данных статистики | 200, пустые ряды | — | «Нет данных за выбранный период» вместо графиков |
| 8 | Нет сети у клиента | — (клиент) | запрос не уходит | баннер «Нет подключения к интернету», введённый текст сохраняется, кнопка «Повторить» |
| 9 | LLM недоступна / таймаут | 503 `LLM_UNAVAILABLE` / 504 `LLM_TIMEOUT` | 1 автоматический повтор; при неудаче — переключение на резервный `LLMClient`, если настроен | «Ассистент временно недоступен, попробуйте через минуту», вопрос остаётся в поле ввода |
| 10 | Обрыв SSE посреди ответа | событие `error` или закрытие потока | частичный ответ не сохраняется как финальный | показать полученный текст с пометкой «Ответ прерван» и кнопкой «Сгенерировать заново» |
| 11 | Внутренняя ошибка сервера | 500 `INTERNAL_ERROR` | логирование с `request_id` | «Что-то пошло не так. Код ошибки: {request_id}» + «Повторить» |
| 12 | Превышен лимит запросов | 429 `RATE_LIMITED` + `Retry-After` | запрос отклонён | «Вы задали много вопросов подряд. Попробуйте через N мин.» |
| 13 | Не авторизован (история) | 401 `UNAUTHORIZED` | — | экран «Войдите, чтобы сохранять консультации» с кнопками входа |
| 14 | Истёк токен | 401 `TOKEN_EXPIRED` | клиент пробует обновить токен через Supabase, при неудаче — выход | «Сессия истекла, войдите снова», текущий ввод не теряется |
| 15 | Нет прав (админка) | 403 `FORBIDDEN` | — | страница «Недостаточно прав» + ссылка на главную |
| 16 | Чужой или несуществующий диалог | 404 `NOT_FOUND` | данные не раскрываются | «Консультация не найдена» + ссылка «Мои консультации» |
| 17 | Неподдерживаемый файл / > 10 МБ | 415 / 413 | файл отклонён | проверка на клиенте до отправки, сообщение с допустимыми форматами и размером |
| 18 | Ошибка индексации документа | статус `failed` | старая редакция остаётся активной | красный статус «Ошибка» и текст причины, кнопка «Повторить индексацию» |
| 19 | Ошибка генерации .docx | 500 `DOCX_ERROR` | — | «Не удалось создать файл, скопируйте текст»; «Копировать» доступна |
| 20 | Не сохранилась оценка | 5xx | — | toast «Не удалось сохранить оценку», чат работает дальше |

### 5.3. Логирование
- Формат JSON: `timestamp`, `level`, `request_id`, `endpoint`, `status`, `latency_ms`, `model_name`, `question_length`, `refusal_type`.
- Запрещено логировать текст вопросов, ответов и данные претензий.
- Ошибки уровня `error` содержат стектрейс и `request_id`, который показывается пользователю.

## 7. Проверка ТЗ с помощью AI

Для проверки полноты и непротиворечивости использовался промпт:

```markdown
Role: Ты — опытный бизнес-аналитик и технический ревьюер.
Task: Проверь техническое задание ниже на полноту, непротиворечивость и техническую реализуемость.
Context: ТЗ и user stories проекта (вставлены ниже). Разработку будет вести один разработчик с AI-агентом за 4–6 недель.
Format:
1. Таблица найденных проблем: раздел → проблема → критичность (высокая/средняя/низкая) → предложение.
2. Список user stories, не покрытых функциональными требованиями, и требований без user stories.
3. Вопросы, которые нужно уточнить у заказчика (не более 7).
```

**Результаты проверки и внесённые правки:**
> _Заполнить после прогона: основные замечания агента и что было исправлено в ТЗ._
