# Применение техники Chain-of-Thought (Шаг 4)

## Задача

**Построить конвейер индексации базы знаний:** загрузить текст Закона РФ «О защите прав потребителей», нарезать его на фрагменты по статьям, посчитать эмбеддинги и сохранить в PostgreSQL + pgvector, а затем реализовать функцию поиска релевантных фрагментов по вопросу пользователя.

**Почему задача сложная и подходит для CoT:** если попросить агента «сделай RAG-индексацию» одним промптом, он смешает разбор документа, работу с моделью эмбеддингов, схему БД и поиск в одном файле, а ошибки в нарезке незаметно испортят качество поиска. Поэтому задача разбивается на шаги, где результат каждого шага проверяется до перехода к следующему.

## Цепочка рассуждений

| Шаг | Что делаем | Результат шага | Проверка перед переходом дальше |
|---|---|---|---|
| 1 | Анализ структуры документа и проектирование формата фрагмента | описание структуры закона и модель `Chunk` | модель согласована, нет противоречий с правилами |
| 2 | Парсер: нарезка текста на статьи и пункты | `rag/chunking.py` + тесты | тесты зелёные, ручная проверка 3–5 фрагментов |
| 3 | Схема БД и индексация (эмбеддинги → pgvector) | миграция `chunks`, `rag/indexer.py` | в таблице N строк, у всех вектор размерности 1024 |
| 4 | Функция поиска и проверка качества на контрольных вопросах | `rag/retriever.py`, отчёт по 10 вопросам | нужная статья в топ-5 минимум у 8 из 10 вопросов |

## Шаг 1. Анализ структуры документа

**Промпт:**

```markdown
Role: Ты — инженер по обработке текстов и RAG-системам.

Task: Проанализируй структуру фрагмента Закона РФ «О защите прав потребителей» ниже и предложи формат фрагмента (чанка) для векторного поиска. Рассуждай по шагам:
1) какие структурные элементы есть в тексте (главы, статьи, пункты, абзацы);
2) какой уровень нарезки лучше для поиска ответов на бытовые вопросы и почему;
3) какие метаданные нужно сохранить, чтобы ассистент мог сослаться на источник;
4) что делать со слишком длинными статьями.

Context: Фрагмент документа (статьи 18–19):
{вставить текст}
Эмбеддинги BGE-M3, рекомендуемая длина фрагмента — до ~1500 символов.

Format: Сначала рассуждение по 4 пунктам, затем итоговая Pydantic-модель `Chunk` с комментариями к полям. Код парсера пока не писать.
```

**Результат:**

> Шаг выполнил агент Claude Code (модель `claude-opus-5-5`) 24.10.2026 в сессии с `CLAUDE.md` проекта. Вместо заглушки `{вставить текст}` агент взял реальный текст закона с КонсультантПлюс (ред. от 28.12.2025): преамбулу и статьи 18, 19, 25.

Рассуждение агента по четырём пунктам (кратко):

1. **Структура.**
   - Преамбула с основными понятиями (потребитель, недостаток, существенный недостаток) идёт до главы I и занимает около 5400 символов.
   - Дальше 4 главы и 55 статей. Есть номера с точкой: 10.1, 16.1, 23.1, 26.1, 26.2, 39.1, 42.1–42.3.
   - Внутри статей — пункты («1.», «3.1.»), внутри пунктов — абзацы, перечни оформлены абзацами с «;».
   - Поверх нормы лежит служебный слой справочной системы: пометки «(в ред. …)», «(см. текст в предыдущей редакции)», утратившие силу пункты и абзацы, вставки «Перспективы и риски споров…» и «- Покупатель хочет…». В начале документа — многострочный «Список изменяющих документов». Всё это около 22% текста.
2. **Уровень нарезки — статья.** Бытовой вопрос обычно закрывается одной статьёй: возврат и замена — ст. 18, сроки — ст. 19, обмен — ст. 25. Если резать мельче, абзац вроде «потребовать замены…» теряет вводную часть и становится непонятным. Если крупнее, в одном векторе смешиваются разные темы. Замер показал, что ключевые статьи длиннее лимита: ст. 18 — 7474 символа, ст. 19 — 5195, ст. 25 — 1603. Значит, делить придётся почти всегда.
3. **Метаданные:** название документа, номер статьи строкой (из-за «23.1»), название статьи, номер части. Заголовок статьи добавляется к тексту при расчёте эмбеддинга, чтобы часть из середины статьи не теряла тему. Глава для ссылки не нужна. Дата редакции хранится на уровне документа (`documents.edition_date`).
4. **Длинные статьи:**
   - делятся по пунктам, соседние пункты объединяются, пока влезают в 1500 символов;
   - пункт длиннее лимита (ст. 18 п. 1 — 1900, п. 3.1 — 2022; ст. 19 п. 2 — 1627) делится по абзацам;
   - абзац длиннее лимита делится по предложениям. Это запасной путь: самый длинный абзац в этих статьях — 1197 символов.

   Перекрытие фрагментов не нужно: границы проходят по структуре документа, а заголовок статьи повторяется в каждой части.

Итоговая модель (`backend/app/rag/models.py`):

```python
class Chunk(BaseModel):
    """Фрагмент нормативного документа — единица векторного поиска и цитирования."""

    model_config = ConfigDict(frozen=True, str_strip_whitespace=True)

    document_title: str = Field(min_length=1)            # «Закон РФ „О защите прав потребителей“» — для ссылки
    article: str | None = Field(default=None, pattern=r"^\d+(\.\d+)*$")  # строка: бывают «23.1»; None — преамбула
    article_title: str | None = None                     # название статьи для карточки источника
    part: int = Field(default=1, ge=1)                   # номер части, если статья делилась
    content: str = Field(min_length=1)                   # текст без заголовка и редакционных пометок

    def heading(self) -> str: ...         # «Статья 18. Права потребителя…» или «Преамбула»
    def embedding_text(self) -> str: ...  # документ + заголовок + текст — то, что уходит в BGE-M3
```

Проверка перед переходом:
- поля совпадают с таблицей из шага 3 (`document_id` и `embedding` добавляются при индексации);
- модель лежит в `rag/` без импорта FastAPI (правило 2.6).

**Что пришлось уточнить / сколько итераций:**

Одна итерация, но анализ реального текста изменил исходные правила:
- преамбула ЗоЗПП — не короткое вступление, а около 5400 символов определений, нужных для поиска («существенный недостаток»). Поэтому она тоже делится на части с `article=None`;
- в план добавлена очистка служебных строк справочной системы, хотя в промпте её не было;
- деление по пунктам дополнено делением по абзацам: в ст. 18 и 19 есть пункты длиннее лимита.
