# Библиотека промпт-шаблонов (структура RTCF)

Каждый шаблон построен по схеме **Role – Task – Context – Format**. Переменные в фигурных скобках `{...}` заменяются перед отправкой агенту. Шаблоны рассчитаны на работу вместе с файлом правил `CLAUDE.md`, поэтому общий стек в них повторяется только там, где это важно для задачи.

| № | Сценарий | Когда использовать |
|---|---|---|
| 1 | Генерация компонента / функции | новая фича по описанию |
| 2 | Рефакторинг | код работает, но плохо читается или медленный |
| 3 | Написание тестов | покрыть существующий код тестами |
| 4 | Исправление ошибок | есть стектрейс, лог или скриншот бага |
| 5 | Декомпозиция задачи | большая задача, непонятно с чего начать |

---

## Шаблон 1. Генерация компонента / функции по описанию

```markdown
**Role:** Ты — Senior {Frontend|Backend} разработчик проекта «ПотребКонсульт», который строго следует правилам из CLAUDE.md.

**Task:** Создай {компонент|функцию|эндпоинт} `{Название}`, который {что делает, 1–2 предложения}.

**Context:**
- Где используется: {страница / сервис / вызывающий код}
- Входные данные: {props / аргументы / тело запроса с типами}
- Выходные данные: {что возвращает или отображает}
- Состояния и граничные случаи: {loading, error, empty, отказ ассистента и т.п.}
- Связанные файлы: {пути к типам, API-клиенту, соседним компонентам}

**Format:**
1. План в 2–5 пунктах и список создаваемых файлов.
2. Полный код каждого файла с путём в заголовке блока.
3. Тест на основной сценарий и один негативный сценарий.
4. Как проверить: команда запуска и что должно получиться.
```

### Пример использования

```markdown
**Role:** Ты — Senior Frontend разработчик проекта «ПотребКонсульт», который строго следует правилам из CLAUDE.md.

**Task:** Создай компонент `AnswerMessage`, который отображает ответ ассистента в чате вместе со списком источников.

**Context:**
- Где используется: `src/features/chat/components/ChatWindow.tsx`, в списке сообщений.
- Входные данные: props `message: AssistantMessage` из `src/features/chat/types.ts`
  (`{ id: string; text: string; sources: Source[]; refusal: boolean }`,
  `Source = { documentTitle: string; article: string; excerpt: string }`).
- Выходные данные: блок сообщения; источники — список чипов «ст. 18 ЗоЗПП», по клику раскрывается цитата.
- Граничные случаи: если `refusal: true` — показать нейтральную плашку «В базе нет ответа на этот вопрос» и ссылку на Роспотребнадзор; если источников нет — чипы не рендерить.
- Связанные файлы: `src/features/chat/types.ts`, `src/components/Chip.tsx`.

**Format:**
1. План и список файлов.
2. Код `AnswerMessage.tsx` и, при необходимости, `SourceChip.tsx`.
3. Тесты Vitest + RTL: отображение источников и режим отказа.
4. Команда `npm run test -- AnswerMessage`.
```

## Шаблон 2. Рефакторинг кода

```markdown
**Role:** Ты — Senior разработчик и ревьюер кода, специализирующийся на {Python/FastAPI | TypeScript/React}.

**Task:** Проведи рефакторинг кода ниже с целью: {читаемость | производительность | соответствие архитектуре | устранение дублирования}. Поведение и публичный интерфейс должны остаться прежними.

**Context:**
- Файл: `{путь}`
- Что не устраивает: {конкретные проблемы}
- Ограничения: {не менять сигнатуры / не добавлять зависимости / сохранить совместимость с тестами}
- Код:
  ```{язык}
  {код}
  ```

**Format:**
1. Список найденных проблем (таблица: проблема → почему плохо → как исправим).
2. Итоговый код целиком.
3. Краткий diff-комментарий: что изменилось и почему.
4. Подтверждение, что существующие тесты проходят без изменений (или какие тесты нужно добавить).
```

### Пример использования

```markdown
**Role:** Ты — Senior разработчик и ревьюер кода, специализирующийся на Python/FastAPI.

**Task:** Проведи рефакторинг функции поиска фрагментов с целью соответствия архитектуре и читаемости. Поведение должно остаться прежним.

**Context:**
- Файл: `backend/app/api/chat.py`
- Что не устраивает: роут сам ходит в БД сырым SQL с f-строкой, считает эмбеддинг внутри роута, порог релевантности захардкожен (0.42), нет логирования.
- Ограничения: не менять URL и формат ответа `/api/chat/ask`; не добавлять зависимостей.
- Код:
  ```python
  @router.post("/ask")
  async def ask(q: dict):
      emb = model.encode(q["question"])
      rows = await db.fetch(f"SELECT * FROM chunks ORDER BY embedding <-> '{list(emb)}' LIMIT 5")
      rows = [r for r in rows if r["score"] > 0.42]
      ...
  ```

**Format:** как в шаблоне.
```

## Шаблон 3. Написание тестов для существующего кода

```markdown
**Role:** Ты — QA-инженер / разработчик, пишущий автотесты на {pytest | Vitest + React Testing Library}.

**Task:** Напиши тесты для `{функция/компонент}` так, чтобы покрыть основные и граничные сценарии.

**Context:**
- Код под тестом:
  ```{язык}
  {код}
  ```
- Внешние зависимости, которые нужно замокать: {БД, LLMClient, HTTP}
- Важные бизнес-правила: {что обязательно должно проверяться}
- Существующие фикстуры: {пути к conftest.py / test-utils}

**Format:**
1. Таблица тест-кейсов: название → входные данные → ожидаемый результат → тип (позитивный/негативный/граничный).
2. Код тестового файла с путём `tests/...`.
3. Команда запуска и ожидаемый результат (сколько тестов, все зелёные).
```

### Пример использования

```markdown
**Role:** Ты — разработчик, пишущий автотесты на pytest.

**Task:** Напиши тесты для функции `split_law_into_articles(text: str) -> list[Chunk]`, которая нарезает текст закона на фрагменты по статьям.

**Context:**
- Код под тестом: `backend/app/rag/chunking.py` (вставлен ниже).
- Зависимостей нет, мокать ничего не нужно.
- Бизнес-правила: каждый фрагмент содержит номер статьи и её заголовок; статья длиннее 1500 символов делится по пунктам, номер статьи сохраняется во всех частях; текст до первой статьи (преамбула) — отдельный фрагмент с `article=None`; пустой текст → пустой список.
- Фикстуры: `tests/fixtures/law_sample.txt` (3 статьи).

**Format:** как в шаблоне.
```

## Шаблон 4. Исправление ошибок и багов

```markdown
**Role:** Ты — опытный разработчик, который ищет первопричину ошибки, а не маскирует симптомы.

**Task:** Найди причину ошибки и исправь её.

**Context:**
- Что делал пользователь / какой запрос: {шаги воспроизведения}
- Ожидаемое поведение: {...}
- Фактическое поведение: {...}
- Ошибка / лог / стектрейс:
  ```
  {текст ошибки}
  ```
- Подозрительный код и путь к файлу:
  ```{язык}
  {код}
  ```
- Окружение: {локально / Docker / версия модели в Ollama}

**Format:**
1. Диагноз: причина в 1–3 предложениях.
2. Исправленный код с путём к файлу.
3. Тест, который падал бы до исправления и проходит после.
4. Как убедиться, что ошибка не повторится в похожих местах.
```

### Пример использования

```markdown
**Role:** Ты — опытный разработчик, который ищет первопричину ошибки, а не маскирует симптомы.

**Task:** Найди причину ошибки и исправь её.

**Context:**
- Шаги: задаю длинный вопрос (≈1800 символов) в чате.
- Ожидаемое поведение: ответ ассистента со ссылками.
- Фактическое: через 30 секунд фронтенд показывает «Ошибка сервера», в логах backend — 500.
- Лог:
  ```

  ```
- Код `backend/app/llm/ollama_client.py` (вставлен ниже), таймаут клиента 30 с.
- Окружение: локально, Ollama, модель 8B на CPU.

**Format:** как в шаблоне.
```

## Шаблон 5. Декомпозиция сложной задачи на подзадачи

```markdown
**Role:** Ты — технический лидер (Tech Lead), который планирует работу для команды из одного разработчика и AI-агента.

**Task:** Разбей задачу «{формулировка большой задачи}» на последовательность подзадач, каждую из которых можно выполнить и проверить за 1–3 часа.

**Context:**
- Цель и критерий готовности всей задачи: {...}
- Что уже есть в проекте: {модули, таблицы, эндпоинты}
- Ограничения: {сроки, железо, нельзя использовать платные API и т.п.}

**Format:**
Таблица: № → подзадача → входные артефакты → результат (артефакт) → как проверить → зависит от.
После таблицы — риски (до 3 пунктов) и с какой подзадачи начать.
Код не писать.
```

### Пример использования

```markdown
**Role:** Ты — технический лидер, который планирует работу для команды из одного разработчика и AI-агента.

**Task:** Разбей задачу «Добавить генерацию черновика претензии продавцу по итогам диалога» на подзадачи.

**Context:**
- Критерий готовности: пользователь нажимает «Составить претензию», заполняет форму (продавец, товар, дата покупки, суть проблемы, требование), получает текст претензии со ссылками на статьи закона и может скопировать или скачать его в .docx.
- Что есть: чат `/api/chat/ask`, `LLMClient`, таблицы `conversations`, `messages`, поиск по `chunks`.
- Ограничения: только локальная модель; персональные данные из формы не сохраняются в БД.

**Format:** как в шаблоне.
```
